# T-6.1 — E1 : décodeur VAE en fp16 (MLX)

Jalon : 6 · Prérequis : T-6.0 · Tier : 2 · ⛔ GATE : non (question d'écoute dans ASK.md)

## Objectif
Savoir si le VAE en fp16 est acceptable : condition nécessaire à tout backend Neural Engine (fp16 seulement).

## À lire
- `plan/13-ios-backend.md` §13.5 ligne E1
- `Sources/YuE2Core/Models/VAE/YuE2VAE.swift` (91 lignes) et `OobleckDecoder.swift` (137 lignes)

## Fichiers à modifier / créer
- `YuE2VAE` : `public enum VAEPrecision { case fp32, fp16 }` ; `init(config:, precision:)` ; les poids sont castés à la précision au chargement (`asType`, eval par tenseur), l'entrée `z` castée, la sortie renvoyée en fp32. La `precondition(z.dtype == .float32)` devient un cast.
- `SnakeBeta` : garde le calcul `sin(x·a)²` dans le dtype courant ; ajouter un contrôle `isfinite` en mode debug (`YUE2_DEBUG`).
- `Sources/YuE2CLI/ParityCommand.swift` : `yue2 parity vae --precision fp16` imprime en plus `PARITY vae_fp16_vs_fp32: snr=<dB> max=<x>` (SNR = 10·log10(Σy32² / Σ(y32−y16)²)) sur `latent_40` et `latent_1100`.
- `DecodeCommand` : `--precision fp32|fp16`.
- `Tests/YuE2Tests/RealVAEParityTests.swift` : test fp16 : SNR > 40 dB, aucun `NaN`.

## Étapes
1. Implémenter ; `yue2 parity vae --precision fp16` ; noter SNR et max abs dans le journal.
2. Paire à écouter : `yue2 decode --latents .local-runs/song-full-bf16/latent.npy --precision fp16 --out .local-runs/vae-fp16.wav` vs l'`audio.wav` fp32 du même dossier.
3. Question dans `tasks/ASK.md` (« fp16 inaudible ? ») avec les deux chemins ; commit `feat(vae): fp16 precision option (E1)`.

## Validation
1. `Scripts/check-build.sh` → `BUILD OK`
2. `bash -c '.xcodebuild/Build/Products/Release/yue2 parity vae --precision fp16 --models-dir "$YUE2_MODELS_DIR" | grep -E "snr|PARITY OK|PARITY FAILED" | tail -3'` → ligne `snr=` puis `PARITY OK vae …`
3. `Scripts/check-tests.sh RealVAEParityTests` → `TESTS OK (≥ 3 tests, 0 skippés)`
