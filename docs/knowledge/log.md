- 2026-09-20 — T-6.4, E4, NAR stack in Core AI: two durable findings beyond the fiche's own outcome (`tasks/JOURNAL.md` has the full numbers). **(1) Lifetime-dependent-value API contract, confirmed a second time**: `NDArray.view(as:)` returns a value whose borrow must be traceable to a named local `let` spanning the whole call site — calling it directly on an unnamed temporary (`NDArrayBridge.ndArray(from: x).view(...)`) or on a bare stored-property read (`self.someND.view(...)`) only gets the compiler a borrow scoped to that one statement, too short to cover a later `InferenceFunction.run(inputs:)` in the same method (`error: lifetime-dependent value escapes its scope`). `CoreAIVAEDecoder.decode` (T-6.3) already used the safe pattern (bind to `let` first) without this being written down as a rule; now it is — any future Core AI bridge code should bind every `NDArray` to a local before `.view(as:)`. **(2) ANE + int8 `coreai.dequantize` is a hard crash, not just imprecise**: `SpecializationOptions(preferredComputeUnitKind: .neuralEngine)` on an asset using `Int8Linear` (weight-only int8 via `torch.ops.coreai.dequantize`) doesn't silently fall back or degrade — it prints `ANE regionCall op not found` during specialization (same warning family as T-6.3's VAE ANE conv-transpose finding) and then aborts the process (`SIGABRT`, exit 134) the first time the function actually runs, with `ANE inference operation failed due to unknown error`. This is `coreai-torch` 0.4.2 on this SDK; the practical rule is: never ship an ANE preference for an asset with int8-dequantize ops without a parity/smoke run confirming the process doesn't abort, not just checking the numeric output. **(3) Core AI GPU is markedly slower than MLX for this workload**: one-shot `bench-coreai-nar` timing (no cooldown/A-B-B-A rigor, informational only per this command's own docstring) showed Core AI GPU ≈7-8× slower than MLX per NAR `velocity` evaluation (205ms→1586ms at L=256, 773ms→7001ms at L=1024), plus a multi-second one-time K/V-to-`NDArray` conversion cost per chunk. Unlike the VAE (T-6.3, where the blocker was precision), here Core AI GPU is numerically correct (`PARITY OK`) but likely not worth shipping purely on throughput grounds — deferred to G-9 (iPhone measurement) per the fiche's own closing criterion, since ANE (the unit this would matter most for on a phone) isn't usable at all yet.
