### 0.3 Comment valider une étape (protocole de validation)

Chaque fiche se termine par une section *Validation* qui n'utilise que **quatre commandes**, dont la sortie a été conçue pour tenir en une ligne lisible :

| Commande | Ce qu'elle fait | Sortie attendue | En cas d'échec |
|---|---|---|---|
| `Scripts/check-build.sh` | `xcodebuild` Release du produit `yue2`, journal complet dans `.local-runs/build.log` | dernière ligne `BUILD OK` | dernière ligne `BUILD FAILED (<n> erreurs)` précédée des 20 premières lignes `error:` — corriger, relancer ; **3 échecs consécutifs sur la même erreur ⇒ `tasks/ASK.md`** |
| `Scripts/check-tests.sh [Suite]` | `Scripts/run-tests.sh -only-testing:YuE2Tests/<Suite>` (ou toute la suite sans argument), journal dans `.local-runs/tests.log` | `TESTS OK (<n> tests)` | `TESTS FAILED` + lignes `✘` ; un test **skippé** parce que `YUE2_MODELS_DIR` est absent compte comme un échec de la fiche si la fiche est tier 2 |
| `Scripts/check-parity.sh <composant>` | `yue2 parity <composant>` (tier 2) et compare aux tolérances de la fiche | `PARITY OK <composant> max=<x> rel=<y>` | `PARITY FAILED` + première divergence (`PARITY <tap>: rel <e>`) |
| `Scripts/check-fixtures.sh` | vérifie que les fixtures `parity/*.safetensors` existent, portent `metadata.kind/seed`, et que `.venv-ref` répond | `FIXTURES OK` | `FIXTURES MISSING <nom>` ⇒ relancer le script Python de la fiche 1.3 |

Règles :
- Les validations se lancent **dans l'ordre de la fiche** et on s'arrête au **premier** échec.
- **Une commande = un appel d'outil, une lecture de sa dernière ligne.** Ne pas relire `.local-runs/*.log` en entier : `grep -n "error:" .local-runs/build.log` puis `read_file` autour de la première ligne.
- Une validation verte ne se « suppose » jamais : la ligne `BUILD OK` / `TESTS OK` doit apparaître dans la sortie de l'outil, et elle est recopiée dans l'entrée de journal.
- Le critère de fin d'une fiche est **exactement** la liste de ses validations vertes ; rien d'autre (pas d'« et j'ai aussi amélioré… »).
- Les mesures de performance ne se font qu'en **Release**, GPU refroidi, et se lisent dans le rapport du profiler, jamais au chronomètre.

**Intégration du profiler (`swift-mlx-profiler` 1.5.0) — recette unique, à appliquer telle quelle (fiches 2.11 et 3.7)** :

```swift
import MLXProfiler

// 1. Une session par run, créée par l'appelant (CLI/GUI), passée au pipeline en paramètre optionnel.
let config = ProfilingConfig(trackMemory: true, exportChromeTrace: true, printSummary: true)
let session = ProfilingSession(config: config)
session.title = "yue2 generate"
session.metadata = ["model": "YuE2-3B", "quant": quant.rawValue, "cot": request.cot, "seed": "\(request.seed)"]
let profiler = MLXProfiler.shared
profiler.enable()
profiler.activeSession = session

// 2. Dans YuE2Pipeline : une phase par étape, catégories fixes (mêmes noms partout, ils deviennent des colonnes de BENCHMARKS.md).
session.beginPhase("1. Model Loading", category: .modelLoad)   … session.endPhase("1. Model Loading", category: .modelLoad)
session.beginPhase("2. Plan (ABC)", category: .generation)     … session.endPhase("2. Plan (ABC)", category: .generation)
profiler.startSemanticGen()                                    … profiler.endSemanticGen(frameCount: semanticTokens.count)   // phase "Semantic Code Generation"
profiler.startFlowMatching()                                   … profiler.endFlowMatching()                                  // phase "Flow Matching"
profiler.startCodecDecode()                                    … profiler.endCodecDecode()                                   // phase "Codec Decode"
profiler.setTTFT(ttftSeconds)                                  // mesuré dans TokenGenerator (premier token de la phase sémantique)
profiler.setAudioDuration(Double(samples) / 48_000)

// 3. Boucles internes : une sous-phase par pas ODE et par tuile VAE, sans snapshot (coût ≈ 2 µs) :
session.beginPhase("ODE step \(k)", category: .custom) … session.endPhase("ODE step \(k)", category: .custom)

// 4. Fin de run (CLI) :
session.finish()
print(session.generateReport())                       // le cadre « PHASE TIMINGS » avec GPU%/CPU%
print(profiler.getTTSMetrics().summary)               // Tokenization/Semantic/Flow/Codec/TTFT/Total/RT factor
try ChromeTraceExporter.export(session: session).write(to: outDir.appendingPathComponent("trace.json"))
```

Validation de l'intégration (fiche 3.7) : `yue2 generate --request examples/song.json --profile --out .local-runs/p1` imprime le cadre avec **exactement** ces phases (`1. Model Loading`, `2. Plan (ABC)`, `Semantic Code Generation`, `Flow Matching`, `Codec Decode`), `TTSMetrics.summary` affiche `RT factor`, et `.local-runs/p1/trace.json` existe et commence par `[` ou `{"traceEvents"`. Le test tier 1 `ProfilingTests` crée une session, ouvre/ferme deux phases et vérifie que `phaseSummaries()` renvoie leurs deux noms avec `durationMs > 0`. Les chiffres reportés dans `BENCHMARKS.md` sont **copiés** de `TTSMetrics.summary`, jamais recalculés.
